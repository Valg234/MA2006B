\chapter{Descripción General}

\section{Propósito del sistema}

El \textbf{Gestor de Identidades y Documentos} es una aplicación web desarrollada para \textbf{Casa Monarca}, organización civil de atención a personas migrantes en Monterrey, Nuevo León. El sistema centraliza la gestión de usuarios, migrantes, solicitudes y documentos internos, con énfasis en el flujo de revisión y firma digital de documentos oficiales mediante criptografía asimétrica (RSA).

El propósito central es reemplazar procesos manuales y en papel por un flujo digital controlado, trazable y seguro, que garantice que cada documento pase por las etapas de revisión y aprobación correctas antes de ser finalizado.

\section{Alcance}

El sistema abarca las siguientes funcionalidades principales:

\begin{itemize}
  \item \textbf{Autenticación y control de acceso} por roles (admin, coordinador, operador, consulta).
  \item \textbf{Gestión de usuarios}: creación, edición, activación/desactivación y asignación de coordinador.
  \item \textbf{Registro de migrantes}: captura de datos personales, migratorios y de atención.
  \item \textbf{Gestor de documentos}: carga, flujo por etapas (V→O→C→A), firma digital RSA y verificación de integridad.
  \item \textbf{Solicitudes push}: flujo de aprobación delegado entre usuarios y coordinadores.
  \item \textbf{Generación de llaves RSA} para coordinadores, con clave privada cifrada por contraseña.
\end{itemize}

El sistema \textbf{no incluye}: módulo de reportes estadísticos avanzados, integración con sistemas externos de migración ni notificaciones por correo electrónico.

\chapter{Arquitectura del Sistema}

\section{Tipo de arquitectura}

El sistema sigue una arquitectura de \textbf{cliente-servidor desacoplada}, donde el frontend y el backend son procesos independientes que se comunican mediante HTTP/JSON:

\begin{itemize}
  \item \textbf{Frontend}: aplicación de página única (SPA) construida con React y servida por Vite.
  \item \textbf{Backend}: conjunto de endpoints PHP independientes, ejecutados por Apache (XAMPP).
  \item \textbf{Base de datos}: MySQL/MariaDB gestionada por XAMPP.
  \item \textbf{Proxy de desarrollo}: Vite redirige las llamadas a \texttt{/api/*} hacia Apache en el puerto 80.
\end{itemize}

\section{Variables de entorno}

El proyecto \textbf{no utiliza archivos \texttt{.env}} en la versión actual. La configuración de la conexión a la base de datos se realiza directamente en \texttt{conexion.php}:

\begin{lstlisting}[style=phpstyle, caption={Archivo conexion.php — variables de configuración}]
<?php
$host       = "localhost";
$usuario    = "CAMBIAR_USUARIO";     // usuario de MySQL
$password   = "CAMBIAR_CONTRASENA"; // contrasena de MySQL
$base_datos = "casa_monarca";

$conexion = new mysqli($host, $usuario, $password, $base_datos);
$conexion->set_charset("utf8");
?>
\end{lstlisting}

\textbf{Importante:} nunca almacenar credenciales reales en el repositorio. Configurar este archivo de forma local antes de ejecutar o desplegar el sistema.

\chapter{Instalación y Ejecución}

\section{Pasos para levantar el sistema}

\begin{enumerate}[label=\arabic*.]
  \item \textbf{Instalar XAMPP} y verificar que Apache y MySQL puedan iniciarse correctamente.

  \item \textbf{Clonar o copiar el proyecto} en el directorio raíz de XAMPP:
  \begin{lstlisting}[style=bashstyle]
C:\xampp\htdocs\casa-monarca-frontend\
  \end{lstlisting}
  Esto es necesario para que Apache sirva los archivos PHP desde la ruta correcta.

  \item \textbf{Iniciar Apache y MySQL} desde el panel de control de XAMPP. Ambos deben aparecer en verde.

  \item \textbf{Crear la base de datos} abriendo \texttt{http://localhost/phpmyadmin}, ir a la pestaña \textbf{SQL}, pegar el contenido de \texttt{database.sql} y ejecutar.

  \item \textbf{Configurar la conexión} editando \texttt{casa-monarca-frontend/conexion.php} con las credenciales de MySQL del entorno local.

  \item \textbf{Instalar dependencias de Node.js} dentro de la carpeta \texttt{casa-monarca-frontend}:
  \begin{lstlisting}[style=bashstyle]
npm ci
  \end{lstlisting}
  El comando \texttt{npm ci} utiliza \texttt{package-lock.json} para instalar versiones exactas y garantizar reproducibilidad.

  \item \textbf{Iniciar el servidor de desarrollo}:
  \begin{lstlisting}[style=bashstyle]
npm run dev
  \end{lstlisting}
  Vite levanta el frontend en \texttt{http://localhost:5173}.

  \item \textbf{Verificar el sistema} accediendo a \texttt{http://localhost:5173} e iniciando sesión con las credenciales del usuario de prueba:
  \begin{itemize}
    \item Email: \texttt{admin@demo.com}
    \item Contraseña: \texttt{casa\_monarca\_pass}
  \end{itemize}
\end{enumerate}

\chapter{Flujos y Lógica de Negocio}

\section{Flujo documental VOCA}

El proceso central del sistema es el flujo de aprobación de documentos, conocido como \textbf{VOCA}:

\begin{figure}[H]
\centering
\begin{Verbatim}[frame=single,rulecolor=\color{gray!40},fontsize=\small]
  [V - Ventanilla]
    Documento creado/recibido
    Acción: Operador o Admin aprueba
          |
          v
  [O - Operador / Verificacion]
    Documento en revision operativa
    Acción: Coordinador firma con clave privada RSA
          |
          v
  [C - Coordinador / Firma]
    Documento firmado digitalmente
    Acción: Admin realiza insercion final
          |
          v
  [A - Insercion final]
    Documento finalizado. Proceso completado.
\end{Verbatim}
\caption{Flujo documental VOCA}
\label{fig:flujo-voca}
\end{figure}

En cualquier etapa, un documento puede ser \textbf{rechazado}, lo que cambia su \texttt{estado\_documento} a \texttt{rechazado} y bloquea cualquier acción posterior sobre él.

\section{Reglas de negocio importantes}

\begin{enumerate}[label=\arabic*.]
  \item \textbf{Control por rol}: cada etapa del flujo solo puede ser ejecutada por el rol autorizado. Un coordinador no puede aprobar en Ventanilla (eso lo hace el operador o admin). Un operador no puede hacer inserción final.
  \item \textbf{Control por coordinación}: los operadores y usuarios de consulta solo ven y actúan sobre documentos cuyo \texttt{coordinador\_id} coincide con su propio \texttt{coordinador\_id}.
  \item \textbf{Integridad del archivo}: al firmar, el sistema calcula el hash SHA-256 del archivo físico y lo firma con OpenSSL. La verificación posterior compara el hash actual del archivo con la firma almacenada, detectando cualquier modificación.
  \item \textbf{Firmas múltiples}: el coordinador principal puede solicitar firmas adicionales de otros coordinadores. El documento solo puede avanzar a Inserción final cuando todas las firmas solicitadas estén en estado \texttt{firmado}.
  \item \textbf{Vigencia del usuario}: al iniciar sesión, el sistema verifica que la \texttt{fecha\_vigencia} del usuario no haya expirado. Si expiró, el acceso es denegado.
  \item \textbf{Estado del usuario}: solo usuarios en estado \texttt{activo} pueden iniciar sesión.
\end{enumerate}

\section{Proceso de firma digital RSA}

\begin{enumerate}[label=\arabic*.]
  \item Al crear un coordinador, el admin (o el propio coordinador) ejecuta \texttt{generar\_llaves\_coordinador.php}. Se genera un par RSA 2048 bits con OpenSSL.
  \item La clave pública se almacena en texto PEM en \texttt{usuarios.clave\_publica}.
  \item La clave privada se cifra con la contraseña elegida y se almacena en \texttt{usuarios.clave\_privada\_cifrada}.
  \item Al firmar un documento, \texttt{firmar\_documento.php}: calcula SHA-256 del archivo, descifra la clave privada con la contraseña, firma el hash con \texttt{openssl\_sign} y almacena la firma en Base64 + folio único.
  \item La verificación (\texttt{verificar\_firma\_documento.php}) recalcula el hash del archivo y lo verifica contra la firma almacenada usando la clave pública.
\end{enumerate}

\chapter{Manejo de Errores}

\section{Estrategia de errores}

El backend siempre devuelve una respuesta JSON estructurada, nunca HTML de error de PHP. Esto se garantiza con:

\begin{itemize}
  \item \texttt{ob\_start()} al inicio de cada endpoint para capturar cualquier salida accidental.
  \item \texttt{ob\_clean()} antes de cada \texttt{echo json\_encode()} para garantizar JSON puro.
  \item \texttt{ini\_set("display\_errors", 0)} para no exponer stack traces a los clientes.
\end{itemize}

El frontend interpreta el campo \texttt{success} de cada respuesta. Si es \texttt{false}, muestra el \texttt{mensaje} al usuario mediante alertas de Bootstrap.

\section{Mensajes de error comunes}

\begin{table}[H]
\centering

\begin{tabular}{p{0.35\textwidth} p{0.51\textwidth}}
\toprule
\textbf{Mensaje} & \textbf{Causa y solución} \\
\midrule
\textit{Datos incompletos} & Faltan campos requeridos en la petición. Revisar el cuerpo del request. \\
\textit{Usuario no encontrado} & Email o ID no existe en la base de datos. \\
\textit{Contraseña incorrecta} & Hash bcrypt no coincide. Verificar datos de acceso. \\
\textit{Usuario inactivo o revocado} & Campo \texttt{estado} distinto de \texttt{activo}. Activar desde AdminPanel. \\
\textit{La vigencia ha expirado} & \texttt{fecha\_vigencia} anterior a la fecha actual. Actualizar desde AdminPanel. \\
\textit{Contraseña de firma incorrecta} & La contraseña no descifra la clave privada RSA. \\
\textit{El coordinador no tiene llaves} & No se han generado llaves RSA. Usar AdminPanel para generarlas. \\

%% CAPÍTULO 13 — SEGURIDAD
%% ============================================================
\chapter{Seguridad}

\section{Autenticación}

\begin{itemize}
  \item Las contraseñas se almacenan como hashes \textbf{bcrypt} con \texttt{password\_hash()} de PHP.
  \item La verificación usa \texttt{password\_verify()}, nunca comparación directa.
  \item Cada ruta protegida del frontend valida la sesión contra el backend mediante \texttt{validar\_sesion.php} antes de renderizar el contenido.
  \item Los datos del usuario activo se almacenan en \texttt{localStorage} del navegador.
\end{itemize}

\section{Firma digital}

\begin{itemize}
  \item Las llaves RSA son de \textbf{2048 bits} generadas con OpenSSL.
  \item La clave privada nunca viaja en texto claro: se almacena cifrada con la contraseña del coordinador.
  \item El algoritmo de firma es \textbf{SHA-256 con RSA} (\texttt{OPENSSL\_ALGO\_SHA256}).
  \item El hash SHA-256 del archivo se recalcula en cada verificación para detectar modificaciones posteriores a la firma.
\end{itemize}

\section{Protección de datos sensibles}

\begin{itemize}
  \item El archivo \texttt{conexion.php} está en \texttt{.gitignore} para evitar que las credenciales reales sean incluidas en el repositorio.
  \item Las claves privadas cifradas se almacenan en la base de datos; solo se pueden usar con la contraseña correcta.
  \item Los endpoints PHP usan \textbf{prepared statements} con \texttt{mysqli} para prevenir inyección SQL.
  \item Los headers CORS están configurados con \texttt{Access-Control-Allow-Origin: *} en desarrollo; deben restringirse a dominios específicos en producción.
\end{itemize}

\section{Buenas prácticas implementadas}

\begin{itemize}
  \item \texttt{ob\_start()} / \texttt{ob\_clean()} para garantizar respuestas JSON puras.
  \item \texttt{display\_errors = 0} en producción para no exponer información del servidor.
  \item Validación de rol en cada endpoint del backend (no solo en el frontend).
  \item Control de vigencia y estado del usuario en cada autenticación.
\end{itemize}

\chapter{Guía de Contribución}

\section{Convenciones de código}

\subsection{Frontend (JavaScript/React)}

\begin{itemize}
  \item Nombrar archivos de componentes con \textbf{PascalCase}: \texttt{GestorDocumentos.jsx}.
  \item Nombrar variables y funciones con \textbf{camelCase}: \texttt{handleSubmit}, \texttt{documentoId}.
  \item Usar \textbf{functional components} con hooks; no usar class components.
  \item Mantener la lógica de fetch dentro del componente que la necesita o en funciones auxiliares del mismo archivo.
  \item Cada página nueva debe añadirse al enrutador en \texttt{App.jsx} con un \texttt{ProtectedRoute} que especifique los roles permitidos.
\end{itemize}

\subsection{Backend (PHP)}

\begin{itemize}
  \item Un archivo PHP por endpoint; el nombre debe describir la acción: \texttt{crear\_usuario.php}.
  \item Usar siempre \textbf{prepared statements} con \texttt{mysqli}; nunca concatenar variables de usuario en SQL.
  \item Iniciar siempre con \texttt{ob\_start()} y usar \texttt{ob\_clean()} antes de cada respuesta.
  \item Toda respuesta debe ser JSON con el campo \texttt{success} (bool) y \texttt{mensaje} (string).
\end{itemize}

\section{Flujo de trabajo con Git}

\begin{enumerate}[label=\arabic*.]
  \item Crear una rama descriptiva desde \texttt{main}:
  \begin{lstlisting}[style=bashstyle]
git checkout -b feature/nombre-de-la-funcionalidad
  \end{lstlisting}

  \item Hacer commits con mensajes claros y en español:
  \begin{lstlisting}[style=bashstyle]
git commit -m "Agrega endpoint para rechazar solicitudes push"
  \end{lstlisting}

  \item Antes de hacer push, revisar que el código no rompe el build:
  \begin{lstlisting}[style=bashstyle]
npm run build
  \end{lstlisting}

  \item Abrir un Pull Request hacia \texttt{main} para revisión del equipo.

  \item Nunca hacer push directo a \texttt{main} sin revisión.
\end{enumerate}

\section{Cómo agregar funcionalidades}

Para agregar un nuevo módulo al sistema seguir estos pasos:

\begin{enumerate}[label=\arabic*.]
  \item \textbf{Backend}: crear el archivo \texttt{api/nombre\_accion.php} con la lógica del endpoint.
  \item \textbf{Base de datos}: si se requiere nueva tabla, agregarla a \texttt{database.sql} con \texttt{CREATE TABLE IF NOT EXISTS}.
  \item \textbf{Frontend}: crear la página en \texttt{src/pages/NombrePagina.jsx}.
  \item \textbf{Ruta}: registrar la nueva ruta en \texttt{App.jsx} con \texttt{ProtectedRoute} y los roles correspondientes.
  \item \textbf{Dashboard}: agregar el acceso visible en \texttt{Dashboard.jsx} para los roles autorizados.
\end{enumerate}

\chapter{FAQ Técnica}

\textbf{¿Por qué el frontend no puede conectarse a la API?}

Verificar que Apache esté corriendo en XAMPP (puerto 80) y que el proyecto esté ubicado en \texttt{htdocs/casa-monarca-frontend/}. Abrir directamente \texttt{http://localhost/casa-monarca-frontend/api/login.php} para confirmar que PHP responde.

\textbf{¿Por qué aparece "Respuesta inválida del servidor" al hacer login?}

PHP está devolviendo HTML de error en lugar de JSON. Revisar \texttt{conexion.php}: las credenciales de MySQL deben coincidir con la instalación local. Abrir \texttt{http://localhost/casa-monarca-frontend/conexion.php} para ver el mensaje de error real.

\textbf{¿Por qué falla la generación de llaves RSA?}

En entornos Windows con MAMP, la ruta del archivo \texttt{openssl.cnf} en \texttt{generar\_llaves\_coordinador.php} debe apuntar a la instalación correcta. En servidores Linux o HostGator, puede eliminarse la clave \texttt{"config"} del array \texttt{\$config} ya que OpenSSL la detecta automáticamente.

\textbf{¿Por qué el operador no puede ver los documentos?}

El operador solo ve documentos cuyo \texttt{coordinador\_id} coincide con su propio \texttt{coordinador\_id}. Verificar que el usuario operador tenga un coordinador asignado en AdminPanel.

\textbf{¿Cómo resetear la contraseña de firma de un coordinador?}

Generar nuevas llaves RSA para el coordinador desde AdminPanel usando una contraseña nueva. Las llaves anteriores quedarán reemplazadas y los documentos firmados con las llaves antiguas seguirán siendo verificables mientras la firma esté almacenada en la base de datos.

\textbf{¿Por qué el puerto 3306 da error al iniciar XAMPP?}

Otro servicio de MySQL está corriendo. En Windows: Administrador de tareas → pestaña Servicios → buscar "MySQL" → Detener. Luego reiniciar MySQL desde el panel de XAMPP.

\textbf{¿Cómo generar el build de producción?}

\begin{lstlisting}[style=bashstyle]
cd casa-monarca-frontend
npm run build
\end{lstlisting}

Los archivos generados en \texttt{dist/} son los que deben subirse al servidor de producción junto con la carpeta \texttt{api/} y el archivo \texttt{conexion.php} configurado.
